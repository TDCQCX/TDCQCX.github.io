## 1. Markdown 是什么，各平台差异在哪

Markdown 由 John Gruber 在 2004 年设计，目标是"用纯文本写出可读的富文本"。它的核心主张是：**源文件本身就该是能直接读的**，标记符号只做最低限度的干扰。

### 为什么会有"方言"

原始 Markdown 规范留了很多模糊地带（比如表格、脚注怎么办），各平台自行扩展出了不同方言：

| 规范 / 方言 | 特点 | 谁在用 |
|---|---|---|
| **CommonMark** | 严格定义、有完整测试用例的标准化版本 | GitHub、Discourse、多数解析器 |
| **GFM** (GitHub Flavored Markdown) | CommonMark + 表格、任务列表、删除线、自动链接 | GitHub、GitLab |
| **Markdown Extra** | 增加脚注、定义列表、表格等 | PHP Markdown Extra、部分静态站点 |
| **MultiMarkdown** | 面向学术写作，支持元数据、引用 | 学术工具链 |

**实践结论**：写 Markdown 时优先用 **CommonMark + GFM 交集**里的语法。表格、任务列表、删除线在 GitHub/博客平台基本通用；脚注、定义列表、内嵌 HTML 的可移植性就差得多。

> 本项目（Hexo + hexo-renderer-marked）支持 CommonMark 与 GFM 的大部分扩展。要预览效果，最可靠的办法是本地 `hexo server` 起个预览服务，而不是凭记忆猜渲染结果。

### 一个自检清单

在不同平台写作前，先确认三件事：

1. **表格支持吗？**（GitHub、博客、大部分文档站：支持）
2. **代码块能用三反引号吗？**（几乎所有现代平台：支持）
3. **内嵌 HTML 允许吗？**（GitHub 会过滤部分标签，博客平台通常允许）

## 2. 标题、段落与换行

### 标题

```markdown
# 一级标题（H1）
## 二级标题（H2）
### 三级标题（H3）
#### 四级标题（H4）
```

也可以用下划线形式，但只支持到二级：

```markdown
一级标题
========

二级标题
--------
```

### 三个实用约定

1. **一篇文档只用一个 H1**。H1 通常就是文档标题，和网页 SEO 的规则一致（本项目的文章页会用 front-matter 的 title 作为 H1，所以正文里如果再写 `# 标题`，页面上会同时出现两个 H1）。
2. **标题层级不要跳级**。H2 下直接写 H4 会让自动生成的目录（TOC）结构错乱。
3. **`#` 后留一个空格**。`#标题` 在多数解析器里不会被识别为标题。

> **本项目的注意点**：主题的 `toc` 功能默认只抓 `min_depth: 1` 到 `max_depth: 3`，也就是 H1 到 H3。写 H4 及更深层级的内容不会出现在右侧目录里。所以组织结构时尽量把主要章节控制在 H2/H3。

### 段落与换行

Markdown 里**单独一个换行不会产生新段落**，它会被合并成同一段的空格：

```markdown
这是第一行
这是第二行

这是另一个段落（前面有空行）
```

渲染结果：前两行合为一段，空行才真正分段。

要强行换行，行尾加**两个空格**（容易看不见，不推荐），或者用一个空行分新段：

```markdown
这行末尾有两个空格··
所以会换行
```

在源代码里每句一行（**语义化换行 / one sentence per line**）是很多技术文档的推荐做法，好处是 diff 更清晰——改一句话只会产生一行变更。

### 常见错误

| 写法 | 问题 |
|---|---|
| 标题和上文之间没有空行 | 部分解析器会把它当成上一段的一部分 |
| 段落之间没有空行 | 两段会被合并 |
| 用 `···` 之类的不可见字符换行 | 别人复制文本时会把空格一起带走 |

## 3. 强调与行内代码

### 强调

```markdown
*斜体* 或 _斜体_
**粗体** 或 __粗体__
***粗斜体***
~~删除线~~        （GFM 扩展）
```

### 为什么推荐用星号

下划线形式的强调有个坑：`snake_case_name` 这种带下划线的标识符可能被误判成强调的一部分。**统一用星号可以避免这个问题**：

```markdown
请使用 my_var_name 变量        → 安全
请使用 my*var_name 变量        → 不会误判（星号前后要有空格才生效）
```

### 行内代码

用反引号包裹：

```markdown
执行 `npm install` 安装依赖。
配置项 `theme.switch` 控制主题切换按钮。
```

**如果内容本身含反引号**，用两个反引号包裹：

```markdown
`` 这段里有一个反引号 ` ``
```

**转义规则**：行内代码里的内容**不会**被解析成 Markdown。所以想展示 `**这两个星号**`，写成反引号包裹即可，不用一个个加反斜杠。

### 强调符号的边界规则

星号要生效，**前后必须是空白或标点，不能紧贴字母**（右边界同理）。这就是为什么 `2*3*4` 里的星号不会触发斜体——这是设计上的刻意行为，避免公式里的星号被误解析。

## 4. 列表与嵌套

### 无序列表

```markdown
- 苹果
- 香蕉
- 橙子
```

`-`、`*`、`+` 都可以，但**同一列表里不要混用**（不同符号会被解析成不同列表）。

### 有序列表

```markdown
1. 安装依赖
2. 启动服务
3. 打开浏览器
```

**序号不必连续**。下面的写法渲染结果完全一样：

```markdown
1. 第一项
1. 第二项
1. 第三项
```

这是个实用技巧：调整顺序时不用重新编号，diff 里也不会因为数字变化而出现噪音。

### 嵌套列表

**子列表要缩进 2 到 4 个空格**（具体数量取决于是哪种父级，多数解析器接受 2 空格）：

```markdown
- 前端技术
  - HTML
  - CSS
    - Flexbox
    - Grid
- 后端技术
  - Java
  - Python
```

### 列表里放代码块或段落

关键是把内容**缩进到与列表项文字对齐**：

```markdown
1. 先安装依赖：

   ```bash
   npm install
   ```

2. 然后启动：

   注意这一步需要网络。

   ```bash
   npm run dev
   ```
```

### 列表的常见坑

| 现象 | 原因 |
|---|---|
| 列表没渲染，显示成一段 | 符号和内容之间少了空格 |
| 嵌套层级不对 | 缩进量不一致（同一层要用相同空格数） |
| 代码块跑出列表外 | 缩进量不够，要和列表项首字对齐 |
| 有序列表从 3 开始 | 前一项实际上被解析成了独立段落 |

## 5. 链接与图片

### 基本语法

```markdown
[链接文字](https://example.com)
[带标题的链接](https://example.com "鼠标悬停显示的文字")
![图片替代文字](/images/pic.png)
```

**`!` 是图片与链接的唯一区别**，记住这个符号及其位置（在最前面）就不会混。

### 参考式链接

当同一个链接在文中出现多次，或 URL 很长影响阅读时，用参考式：

```markdown
本项目使用 [Hexo][hexo] 构建，主题是 [Async][async]。

[hexo]: https://hexo.io/
[async]: https://github.com/MaLuns/hexo-theme-async
```

定义部分可以集中放在文末。这样正文更干净，链接变更时也只需改一处。

### 图片作为链接

需要"点击图片跳转"时，把图片语法嵌进链接语法：

```markdown
[![替代文字](/images/badge.svg)](https://example.com)
```

### 图片路径的三种写法

| 写法 | 适用 | 说明 |
|---|---|---|
| `/images/pic.png` | 站点内绝对路径 | 本项目推荐，部署后路径稳定 |
| `./pic.png` | 相对当前文件 | 文件移动后容易失效 |
| `https://…` | 外链 | 对方站点挂掉就裂图，**不推荐** |

> **本项目的实践**：文章图片统一放在 `source/images/posts/`，引用时写 `/images/posts/xxx.png`。外链图片（如 shields.io 徽章）在源站不可用时会变成裂图，本项目已把正文里用到的外链图片全部本地化。

### 自动链接

GFM 会把裸 URL 自动变成链接：

```markdown
https://example.com
```

但**不要依赖这个行为**，因为并非所有平台都支持。显式写成 `[https://example.com](https://example.com)` 或 `<https://example.com>` 更稳。

### 图片的可访问性

**替代文字（alt）不是可选项**。它有三个作用：

1. 屏幕阅读器会朗读它，这是无障碍访问的基础；
2. 图片加载失败时显示的文字；
3. 搜索引擎用它理解图片内容。

```markdown
<!-- 差: 无意义 -->
![](/images/chart.png)

<!-- 好: 说明图片在讲什么 -->
![2026 年 Q1 到 Q3 的接口响应时间逐月下降趋势图](/images/chart.png)
```

## 6. 引用、分隔线与转义

### 引用

```markdown
> 这是一段引用。
> 可以有多行。
>
> 空行加 > 可以分出新段落。
```

### 嵌套引用

```markdown
> 外层引用
>
> > 嵌套的引用
```

引用块里可以放列表、代码块、表格等任意元素。

### 分隔线

**三个或更多的连字符、星号或下划线**单独成行：

```markdown
---

***

___
```

三个写法渲染结果相同。推荐统一用 `---`。

> **易错点**：如果上一行是文字且**没有空行**，`---` 会被解析成"二级标题的下划线"而不是分隔线：
>
> ```markdown
> 一些文字
> ---          ← 这会被当成二级标题！
>
> 一些文字
>
> ---          ← 这样才是分隔线
> ```

### 转义

需要显示 Markdown 特殊字符本身时，前面加反斜杠：

```markdown
\\* 这不是斜体的开始
\\# 这不是标题
\\[ 这不是链接
```

可转义的字符包括：

```
\\ ` * _ { } [ ] ( ) # + - . ! | > ~
```

**方括号的实用场景**：写 `数组[0]` 时，如果后面恰好接了括号可能被解析成链接，用 `数组\\[0\\]` 更保险。

## 7. 代码块与语法高亮

### 围栏代码块（推荐）

用三个反引号包裹，并在开头标注语言：

````markdown
```javascript
function hello(name) {
  return `Hello, ${name}`;
}
```
````

**一定要标注语言**。它带来三个好处：

1. 语法高亮（本项目使用 highlight.js）；
2. 部分平台会提供复制按钮、行号、折叠（本项目的主题支持这三项）；
3. 阅读者能立刻知道这段是哪种语言。

### 常用语言标识

```markdown
```bash          shell 命令
```javascript    JavaScript
```typescript    TypeScript
```python        Python
```java          Java
```sql           SQL
```json          JSON
```yaml          YAML
```html          HTML
```css           CSS
```diff          差异对比
```

### diff 高亮

标注 `diff` 并给增删行加上 `+` / `-` 前缀，会得到红绿高亮：

````markdown
```diff
- 旧的一行
+ 新的一行
```
````

### 代码块里包含反引号怎么办

外层用**更多数量的反引号**包裹：

`````markdown
````markdown
```javascript
console.log("嵌套示例");
```
````
`````

### 缩进式代码块（不推荐）

四个空格缩进也能生成代码块，但**无法标注语言**，也没有语法高亮：

```markdown
    这是缩进式代码块
    没有语法高亮
```

新文档统一用围栏式。

### 行内代码 vs 代码块的选择

- 只有一个标识符、命令名、文件名 → 行内代码 `` `npm install` ``
- 有换行、有多行、需要高亮 → 代码块

**不要用行内代码写多行命令**，那会让读者很难复制。

## 8. 表格

基本语法：

```markdown
| 左对齐 | 居中 | 右对齐 |
| :--- | :---: | ---: |
| 内容 | 内容 | 内容 |
| 长内容 | 内容 | 内容 |
```

### 对齐控制

分隔行里的冒号决定对齐方式：

| 写法 | 对齐 |
|---|---|
| `:---` | 左对齐 |
| `:---:` | 居中 |
| `---:` | 右对齐 |
| `---` | 默认（多数平台左对齐） |

### 表格的三个限制

1. **单元格里不能直接换行**。需要多行内容时用 `<br>`：
   ```markdown
   | 项 | 说明 |
   |---|---|
   | 参数 | 第一行<br>第二行 |
   ```
2. **管道符需要转义**。内容里有 `|` 时写成 `\\|`。
3. **表格和上文之间必须有空行**，否则不会被识别。

### 表格与列表的选择

**两列、内容较长时，用列表或定义列表更好读**：

```markdown
<!-- 表格: 长文本会被挤成两行以上, 阅读体验差 -->
| 配置项 | 说明 |
|---|---|
| `theme.default` | 设置默认主题模式，可选 style-light、style-dark、auto，其中 auto 表示跟随系统深浅色偏好 |

<!-- 列表: 同样的信息更易读 -->
- **`theme.default`** — 设置默认主题模式。可选 `style-light`、`style-dark`、`auto`，其中 `auto` 表示跟随系统深浅色偏好。
```

### 给表格加说明

表格本身没有标题机制。习惯做法是在表格**上方**加一行粗体或斜体说明：

```markdown
**表 1：常用 HTTP 状态码**

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 404 | 未找到 |
```

## 9. 任务列表、脚注与其他扩展

### 任务列表（GFM）

```markdown
- [x] 已完成的任务
- [ ] 未完成的任务
- [ ] 另一个待办
```

在 GitHub 的 issue / PR 描述里，这是**可直接点击勾选**的交互式清单。

### 脚注

```markdown
这句话需要引用来源[^1]。

[^1]: 这里是脚注内容，会显示在文末。
```

**注意**：脚注是扩展语法，GitHub 支持，但部分博客平台和解析器不支持。不确定时改用行内括号说明或文末"参考"章节。

### 定义列表

```markdown
术语
: 术语的解释
```

同样属于扩展语法，可移植性差。**更稳的替代是粗体加冒号**：

```markdown
**术语**：术语的解释
```

### 折叠内容

Standard Markdown 没有折叠语法。GitHub 支持用 HTML `<details>` 实现：

```markdown
<details>
<summary>点击展开</summary>

这里是被折叠的内容。

</details>
```

**`<summary>` 后必须有一个空行**，否则里面的 Markdown 不会被解析。

### 目录

CommonMark 没有自动目录语法。常见做法有三类：

1. **手写锚点目录**（可移植性最好，但要手动维护）：

   ```markdown
   ## 目录
   
   1. [第一节](#1-第一节)
   2. [第二节](#2-第二节)
   ```

2. **依赖平台自动生成**。GitHub、GitLab、多数博客主题会自动给标题加 id 并支持 `[文字](#锚点)` 跳转。

3. **用工具生成**，如 `markdown-toc`、VS Code 插件。

> **本项目**：主题的 `toc` 功能会自动读取 H1-H3 生成侧边目录，所以**不需要在正文里手写目录**。但像本文这样在开头放一份带链接的目录，能让读者快速了解结构——而且因为标题层级固定，锚点也比较稳定。

### 锚点命名规则

自动生成的锚点通常遵循这个规律：

| 原标题 | 生成的锚点 |
|---|---|
| `## 1. Git 到底解决什么问题` | `#1-git-到底解决什么问题` |
| `## 常见问题 FAQ` | `#常见问题-faq` |

大致是：转小写、空格换成连字符、去掉大部分标点。**含中文的锚点在不同平台上的处理不一致**（有的保留中文，有的转成 URL 编码），所以跨平台引用时，手写目录里的锚点最好实测一次。

## 10. 写作规范建议

### 结构层面

1. **开头写一段导语**。用两三句话说明"这篇文档解决什么问题、读者需要什么前置知识、读完能得到什么"。
2. **先给结论，再给论证**。技术文档不是悬疑小说。
3. **每节聚焦一个主题**。一节超过 300 行时考虑拆分。
4. **用小标题当路标**。读者是扫描式阅读的，标题要能独立传达信息。

### 句子与用词

1. **一句话一件事**。长句拆成短句。
2. **统一术语**。同一概念不要一会儿叫"仓库"、一会儿叫"资源库"。
3. **代码里的标识符用行内代码标注**：`config.yml`、`npm run build`。
4. **避免"显然""简单来说"**。对读者来说可能一点都不显然。
5. **中英文之间留空格**（中文排版惯例）："使用 Node.js 运行"而不是"使用Node.js运行"。

### 代码示例的规范

1. **必须能跑**。给出完整可复制的最小示例，不要留 `// 省略` 之后就期待读者能补全。
2. **标注语言**，见第 7 节。
3. **说明预期输出**，让读者能自检：

   ````markdown
   ```bash
   node -v
   # 输出示例: v20.11.0
   ```
   ````

4. **命令和输出分开**。别把输出混在命令块里让人分不清哪行该敲。
5. **危险命令要标注警告**。涉及删除、覆盖、重置历史的命令，明确写出后果。

### 加粗的使用

**整段都是粗体等于没有粗体**。加粗应该留给"扫一眼就必须看到"的信息：

- 关键结论
- 危险警告
- 与常见误解相反的要点

### 行长度

源码每行控制在 80-120 字符以内。好处：

- 在窄编辑器里不用横向滚动；
- Git diff 更易读；
- 评审时更容易定位改动。

## 12. 常见问题 FAQ

**Q：为什么我的换行不生效？**

Markdown 里单个换行不算换行。要么**空一行**分新段，要么在行尾加两个空格。另外可以开启解析器的 `breaks` 选项（GitHub 评论框就是这种模式），但源文件在其他平台渲染结果会不同，可移植性差。

**Q：`*` 和 `_` 做强调有区别吗？**

渲染结果一样。但 `_` 在 `snake_case` 这类标识符旁容易被误判，**统一用 `*` 更安全**。

**Q：表格里的内容太长怎么办？**

改用列表。或者用 `<br>` 手动断行，但单元格宽度是固定的，内容多了依然会很难读。

**Q：怎么在 Markdown 里写 HTML？**

直接写就行，多数平台允许。但注意：GitHub 会过滤部分标签和所有 `class`/`style` 属性；有的平台完全禁用 HTML。**HTML 越少，可移植性越好。**

**Q：图片不显示，通常是什么原因？**

按这个顺序查：

1. 路径大小写（Linux 服务器区分大小写，Windows 本地不区分——这是最常见的坑）；
2. 路径类型（绝对 `/images/a.png` 还是相对 `./a.png`，相对路径会随文章位置变化）；
3. 文件是否真的存在于输出目录；
4. 文件名里的空格或中文是否被正确编码。

**Q：有序列表的编号必须连续吗？**

不必。全部写 `1.` 也能正确渲染，这是推荐做法（调整顺序时 diff 更干净）。

**Q：怎么让代码块里的反引号正常显示？**

外层用更多的反引号包裹，见第 7 节。

**Q：Markdown 能写数学公式吗？**

标准 Markdown 不支持。但很多平台（GitHub、Jupyter、本项目的 KaTeX 集成）支持 `$...$` 和 `$$...$$`。这属于扩展，跨平台前先确认目标环境。

**Q：文档之间怎么互相引用？**

用相对路径的 Markdown 链接：`[另一篇](../guide/setup.md)`。如果用绝对 URL，部署到不同域名后就要全部改一遍。

**Q：`README.md` 和 `README.rst` 有什么区别？**

`.md` 是 Markdown，`.rst` 是 reStructuredText。后者在 Python 生态（Sphinx 文档）里更常见，表达力更强但语法更啰嗦。**非 Python 项目统一用 Markdown 就行。**

**Q：写文档和写代码一样需要评审吗？**

技术文档的准确性和代码同等重要——错误的文档会让人踩坑而且更隐蔽。建议文档走和代码一样的评审流程。
