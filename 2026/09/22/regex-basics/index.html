正则表达式基础教程 — 语法、实战与避坑

正则表达式（regex）是描述文本模式的迷你语言。它强大到能一行完成复杂校验，也危险到能写出让服务器 CPU 打满的表达式。
这篇教程从最基本的元字符讲到回溯与 ReDoS，目标是让你既能写出正确的正则，也知道什么时候不该用正则。

1. 正则是什么，什么时候不该用

正则表达式用一个模式字符串描述”哪些文本算匹配”。比如 \\d{3}-\\d{4} 描述”3 位数字、连字符、4 位数字”，能匹配 555-1234。

它适合处理结构简单、上下文无关的文本：

  • 校验手机号、邮箱、日期格式；
  • 从日志里提取 IP、时间戳、状态码；
  • 批量查找替换；
  • 切分格式规整的字符串。

这四种情况不要用正则

1. 嵌套结构。 正则本质上处理的是正则语言，无法匹配任意深度的嵌套括号、标签、JSON/HTML。解析这类内容要用真正的解析器（如 JSON.parse、HTML 解析库）。

2. 涉及语义校验。 比如”邮箱是否真实存在”、”日期是否是合法日期”（2025-02-30 格式正确但不存在）、”身份证校验位是否正确”。正则可以挡住格式错误，但最终的语义校验要在代码里做。

3. 性能敏感且可预计算的场景。 高频调用时，预编译正则（见第 8 节）或改用字符串方法会更快。

4. 简单的字符串操作。 找子串、判断前缀，用 includes()、startsWith() 就够，不必上正则。

判断标准：如果你的正则长到需要写注释才看得懂，多半说明这个任务该用解析器或拆成多步。

4. 锚点与边界

锚点不匹配字符，只匹配位置。

锚点 含义
^ 字符串开头（多行模式下为行首）
$ 字符串结尾（多行模式下为行尾）
\\b 单词边界
\\B 非单词边界

为什么校验一定要加 ^ 和 $

这是表单校验里最常见的漏洞——忘了锚定，导致校验形同虚设。

单词边界的用处

\\b 的判定基于 \\w：一侧是单词字符、另一侧不是，那里就是边界。注意中文和空格之间不算单词边界，中文场景下 \\b 通常不管用。

默认情况下量词是贪婪的：尽可能多地匹配。

7. 断言：不消费字符的条件

断言（lookaround）检查某个位置前后是否符合条件，但不把这些字符算进匹配结果。

语法 名称 含义
(?=...) 先行断言 后面必须是什么
(?!...) 否定先行断言 后面不能是什么
(?<=...) 后行断言 前面必须是什么
(?<!...) 否定后行断言 前面不能是什么

实用场景：密码强度校验

用多个先行断言叠加条件，比写一长串复杂分支清晰得多：

拆开看：^(?=.*[a-z]) 检查”某处有小写字母”，(?=.*[A-Z]) 检查大写，(?=.*\\d) 检查数字，(?!...) 部分最后统一限定长度。

兼容性提醒：后行断言（(?<=)）在较旧的浏览器和部分运行时里不支持。若需兼容老环境，改用捕获分组 + $1 提取。

10. 性能陷阱与 ReDoS

回溯：正则变慢的根源

正则引擎（NFA 类型）在匹配失败时会回溯——退回到上一个选择点，换一条路再试。选择点越多，可能的路径就越呈指数增长。

看这个危险的正则：

用它测试 "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaX"（29 个 a 加一个 X）。引擎会尝试所有把 a 分给内外层 + 的组合，路径数是 2 的幂级。30 个字符就足以让 CPU 卡住几秒，40 个字符可能卡几分钟。

这就是 ReDoS（正则表达式拒绝服务）。攻击者只要提交一个精心构造的字符串，就能让你的服务线程被占满。

引发 ReDoS 的典型模式

危险写法 问题
(a+)+ 嵌套量词，同一段字符有多种切分方式
(a|aa)+ 重叠的分支选择
(.*)* 通配符被重复包裹
(\\w+\\s?)* 相邻的可选量词

共同特征是：存在”同一段输入可以被多种方式分配”的结构。

怎么写才安全

  1. 避免嵌套量词。需要”至少一个”用 +，不要写成 (x+)+。

  2. 用否定字符类替代 .*?，消除不必要的回溯（见第 6 节）。

  3. 让分支互斥。把互不重叠的分支放在前面，减少尝试。

  4. 给输入设上限。校验前先判断长度，超长直接拒绝。这是最省事也最有效的一道防线。

  5. 给正则加超时。部分运行时支持超时参数（如 .NET 的 Regex 构造函数、Python 的 regex 模块）。Node.js 没有内置超时，需要靠输入长度限制或换用 RE2 这类不会回溯的引擎。

  6. 核对用户可控的正则输入。如果应用允许用户自定义正则（搜索、过滤、脱敏规则），必须限制长度并拒绝危险结构，否则等于把 ReDoS 入口对外开放。

实践建议：任何用户输入参与的正则，都当作”可能被恶意构造”来对待：限长度 + 避免嵌套量词 + 服务端有整体超时。

11. 调试与可读性建议

用工具调试，别靠脑内推演

复杂的正则用在线调试器验证，能实时看到匹配和分组结果：

  • regex101.com — 支持多语言引擎，会逐步解释每个分组的含义，还能提示潜在的灾难性回溯；
  • debuggex.com — 把正则画成铁路图，理解分组结构很直观。

养成习惯：写完先测边界用例——空字符串、超长输入、含特殊字符、多个匹配、不该匹配的相似串。

12. 常见问题 FAQ

Q：.test() 结果为什么忽真忽假？

因为正则带了 g 标志，test() 会从上一次的 lastIndex 继续找。要么去掉 g，要么每次重置 re.lastIndex = 0。

Q：\\d 能匹配中文数字吗？

不能。\\d 只匹配 ASCII 的 0-9。要匹配中文数字得显式写 [零一二三四五六七八九十]，或使用 Unicode 属性转义（需 u 标志）。

Q：为什么 [^"]* 比 .*? 好？

[^"]* 直接声明”内容里不能有引号”，一步到底不需要回溯；.*? 要靠反复试探和回退才能停下。语义更明确，性能也更好。

Q：怎么匹配换行符？

默认 . 不匹配换行。加 s 标志（dotAll）让 . 包括换行，或显式用 [\\s\\S] 这个经典写法兼容旧环境。

Q：邮箱校验用一条正则就够了吗？

格式可以用正则挡掉明显错误的输入，但唯一可靠的验证是发一封确认邮件。另外 RFC 允许的合法邮箱格式极其复杂，追求”完美正则”往往得不偿失——常见做法是用一条宽松的格式正则（拒绝明显非法输入）+ 发送验证邮件。

Q：正则能解析 HTML / JSON 吗？

不能可靠解析。嵌套结构超出正则语言的能力范围，遇到深层嵌套或特殊字符就会失败。用专门的解析器：浏览器里 DOMParser、Node 里用 HTML 解析库，JSON 用 JSON.parse。

Q：^ 和 $ 在多行文本里怎么用？

加 m 标志后，^ 和 $ 匹配每一行的首尾。不加时它们只匹配整个字符串的开头和结尾。处理逐行日志时通常需要 m。

Q：怎么验证我的正则不会被 ReDoS 攻击？

重点看有没有嵌套量词（(x+)+）、重叠分支（(a|aa)+）、以及 (.*)* 之类的结构。用 regex101 会给出灾难性回溯警告，再把最长的恶意输入（同一字符重复几千次）喂进去实测耗时。
